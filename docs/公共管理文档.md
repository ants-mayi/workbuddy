## 三、控制台项目通则（脚手架模式）

1. **80/20 架构**：`engine/`（core.py、web.py、cli.py、index.html）是通用引擎；项目只写 `config.py` 的 PROFILE。新项目由脚手架 `generate.py` 生成。
2. **引擎升级流程**：先改脚手架 `_scaffold\engine\`，再同步到各项目副本（目前 2 个：`env`、`hfctl`——hfctl 是自包含实现，需手工移植）。
3. **index.html 唯一事实源**：各项目的 `web.py` 直读 `engine/index.html`（INDEX_DIR = 脚本所在目录），**不存在 web/ 副本**，改版只改 engine/ 下的文件。
4. **端口自愈**：启动时占用者若是本项目旧服务自动关闭复用端口，其它程序则 +1 顺延；实际端口记录在项目根 `.web.port`。CLI 传 `HFKIT_WEB_PORT` 环境变量避免二次决策。
5. **CLI 传 Web 端口必须走环境变量**，不要在命令行参数里二次决策。

## 四、文档编写规范（本项目沉淀）

1. **标题 slug 规则（全项目统一，前端/校验/书写三方一致）**：GitHub 风格——小写、剥离标点（含全角 `（）【】《》、`）、**每个空白字符各转一个 `-`**（`\s` 不是 `\s+`）；重复标题靠前端 `-1` 后缀去重，写链接时避免引用重复标题。
2. **跨文档链接写 `xx.md#锚点`**，文内锚点写 `#锚点`；写完跑 `_check_links.py` 一键回归。
3. **marked v12 renderer 注册必须用 `marked.use({renderer:{heading(){}}})`**；顶层 `use({heading: fn})` 会被静默忽略 → 标题无 id → 所有锚点失效（本项目真实踩坑）。
4. **命令/路径进 HTML 一律 `data-*` 属性 + dataset 读取**，禁止拼进 onclick 字符串（单引号命令会导致属性提前闭合）。
5. **外部快捷键/命令资料必须逐条核验**（两份外部手册共核出 10+ 处真实错误），并标注核对日期；版本分界类结论要注明"以 `--version` 实测为准"。
6. **文档落盘前跑三件套**：`_check_links.py` + marked 渲染表格列数检查 + （涉及跳转时）jsdom DOM 测试。

## 五、Web 控制台规范

1. **必须禁缓存**：`@app.after_request` 设 `Cache-Control: no-store`、去 ETag/Last-Modified——否则每次改版都被浏览器缓存坑。
2. **标题 id 不依赖 marked**：渲染后 `querySelectorAll('h1..h6')` 统一补 id（jsdom 测试已验证此方案）。
3. **左侧二级目录**：文档数据存 `window.__DOCS` 全局缓存；目录点击 → show 面板 → 切 tab → `setTimeout(0)` 滚动。
4. **滚动兼容性**：不要用 `requestAnimationFrame`（jsdom 没有），用 `setTimeout(0)`，浏览器同样有效。

## 八、AI 会话协作注意事项

- **PowerShell 5.1 无 `?:` 三元、无 `??`、无 `&&`**；输出编码默认 UTF-16，处理 UTF-8 文件须显式 `-Encoding utf8`。
- **Bash 直接 `cmd.exe`/后台 `&` 会被安全策略拦截**：系统信息用 PowerShell CIM/Get-*；长服务用 run_in_background 受管任务。
- **本机默认 python（WorkBuddy 内置 3.13）没有 flask**；flask 在 G 盘 conda pytorch 环境。
- **jsdom 无 `requestAnimationFrame`、无 `fetch`**（后者需 stub）。
- **事实源优先**：涉及本机环境配置，先读 `电脑开发环境信息.md` 再操作，不要凭记忆猜；新采集到的事实**补充回该文档**。

## 九、事实核验三层法（2026-11-17 教训固化，强制执行）

> 背景：缓存面板核查中，路径"存在性"都验证过，但 Maven 仓库指向错误直到用户第三次追问、
> 沿 `mvn → 安装目录 → conf/settings.xml → localRepository` 生效链路才被发现。
> 教训：**存在性 ≠ 正确性。配置类信息必须核到第三层才算完成。**

| 层 | 检什么 | 方法 | 只做到这层的风险 |
| --- | --- | --- | --- |
| ① 存在性 | 路径/文件是否存在、大小 | Test-Path / 测量 | 无法发现"指向了错误但恰好存在的路径" |
| ② 内容 | 配置文件**读了没有** | 打开 settings.xml/.condarc/.npmrc 等读全文 | 内容里的自定义项（localRepository、pkgs_dirs）被漏掉 |
| ③ 生效链路 | 工具**实际用哪个** | `mvn -v`→安装目录 conf；`npm config get cache`；`pip cache dir`；`conda config --show` | 用户级/全局/环境变量多层配置覆盖关系搞反 |

**执行规则**：
1. 凡新建/修改"配置文件路径"类面板或文档条目，①②③三层全部走完才允许标注"已核验"；只做①的结论一律注明"仅存在性核验"。
2. 核验产出的新事实（如 settings.xml 自定义仓库）**当轮同步写回事实源手册**，不等用户提醒。
3. 自查清单里凡是"检查 XX 是否正确"的请求，默认按三层法执行，不问用户要不要做深。
