## 一、本机环境本身的问题与隐患

> 这些是**采集本机环境时发现的真实问题**，不是工具使用错误。使用时需特别注意。

### 1.1 Python 多版本混用，`python` 与 `pip` 指向不一致 ⚠️ 高发

| 项 | 实际情况 |
| --- | --- |
| Bash 中的 `python` | 3.13.14（WorkBuddy 内置目录 `C:\Users\marco\.workbuddy\binaries\python\...\3.13.12`） |
| `pip` 指向 | 3.14（`D:\wofkIns\Python\Python314\Scripts\pip.exe`） |
| conda base | 3.13.9（`D:\wofkIns\anaconda3`） |
| 验证脚本实测 | 3.13 的 pip 为 26.1.2，3.14 的 pip 为 26.1.1，版本也不同 |

- **解决**：一律用 `python -m pip install xxx`（装到当前解释器）；最好为每个项目建虚拟环境。
- **关联**：环境文档第 7 节；验证脚本 pip 条目的 ①/② 层。

## 二、工具与开发过程中的技术问题（踩坑与解决）

> 这些是**做环境采集、写验证脚本时踩的技术坑**，重点是解决方案与可复用代码。

### 2.1 Bash 中直接调用 `cmd.exe` 被安全策略拦截

- **现象**：在 Bash 里执行 `cmd.exe /c ver` 等被安全策略拒绝。
- **解决**：系统级信息改用 **PowerShell 的 CIM / `Get-*` 命令**采集，例如 `Get-CimInstance Win32_Processor`、`Get-CimInstance Win32_OperatingSystem`。
- **经验**：Bash 工具与 PowerShell 工具各司其职，需要系统信息时直接用 PowerShell 工具。

### 2.2 PowerShell 经 subprocess / 从 Bash 调用也被拦截

- **现象**：`powershell.exe -NoProfile -Command "..."` 通过 Bash 或在 Python subprocess 中调用被安全策略拦截。
- **解决**：不要跨工具链套娃调用——PowerShell 命令直接用 PowerShell 工具执行；Python 脚本里不要依赖 `powershell.exe`。

### 2.3 Windows 下 `.cmd` / `.bat` 命令 subprocess 调用返回空

- **现象**：`subprocess.run(["npm","-v"])` / `mvn` / `code` / `pip` 返回空或找不到，因为这些是 `.cmd`/`.bat` 脚本，不是 `.exe`。
- **解决**：写一个 `resolve_cmd()`，用 `where.exe <name>` 解析真实路径（优先 `.exe`，其次 `.cmd`/`.bat`），再用完整路径调用：
  ```python
  def resolve_cmd(name):
      rc, out = run(["where.exe", name])
      if rc == 0:
          for line in out.splitlines():
              p = line.strip()
              if p.lower().endswith((".exe", ".cmd", ".bat")):
                  return p
      return name
  ```
  然后 `run([resolve_cmd("npm"), "-v"])`
- **关联**：`环境验证脚本.py` 的 `run()` / `resolve_cmd()`。

### 2.4 `py("-m pip ...")` 函数用法错误

- **现象**：封装的 `py(code)` 只执行 `python -c <code>`，传 `"-m pip --version"` 会被当成代码，报错。
- **解决**：需要给解释器传参数时，直接用 `sys.executable` + 参数：
  ```python
  run([sys.executable, "-m", "pip", "--version"])
  ```
- **原则**：`python -m pip` 能保证 pip 归属当前解释器，正好规避 1.1 的多版本问题。

### 2.5 `sc.exe` 服务查询被安全策略拦截

- **现象**：`subprocess.run(["sc.exe","query",name])` 被拦截，服务检查全部失败。
- **解决**：用 **ctypes 直接调 Windows 服务 API**（`advapi32`），不依赖外部 exe：
  ```python
  import ctypes
  from ctypes import wintypes
  a = ctypes.WinDLL("advapi32", use_last_error=True)
  a.OpenSCManagerW.restype = wintypes.SC_HANDLE
  a.OpenSCManagerW.argtypes = [wintypes.LPCWSTR, wintypes.LPCWSTR, wintypes.DWORD]
  a.OpenServiceW.restype = wintypes.SC_HANDLE
  a.OpenServiceW.argtypes = [wintypes.SC_HANDLE, wintypes.LPCWSTR, wintypes.DWORD]
  a.QueryServiceStatus.restype = wintypes.BOOL
  a.QueryServiceStatus.argtypes = [wintypes.SC_HANDLE, ctypes.c_void_p]
  a.CloseServiceHandle.argtypes = [wintypes.SC_HANDLE]
  # 状态值：1=STOPPED 4=RUNNING
  ```
- **关联**：`环境验证脚本.py` 的 `service_state()`。

### 2.6 ctypes 64 位句柄被截断（返回 NOT_FOUND）

- **现象**：未显式声明 `restype`/`argtypes` 时，`OpenSCManagerW` 返回的 64 位句柄被默认按 32 位 `int` 截断，句柄失效，`OpenServiceW` 全部失败。
- **解决**：对**所有返回句柄的函数**显式设置 `restype = wintypes.SC_HANDLE`，并声明 `argtypes`（见 2.5 代码）。
- **教训**：ctypes 默认 `restype` 是 `c_int`，64 位 Windows 下指针/句柄必须显式声明。

### 2.7 `QueryServiceStatus` 状态读不到（返回 UNKNOWN）

- **现象**：句柄正常但 `QueryServiceStatus` 返回失败，状态读不出来。
- **解决**：必须设 `restype = wintypes.BOOL`，第二个参数用 `ctypes.c_void_p` 并传 `ctypes.byref(status)`；`SERVICE_STATUS` 结构体 7 个字段均为 `wintypes.DWORD`。调试确认 `state=4` 即 RUNNING。
- **关联**：`环境验证脚本.py` 的 `service_state()`。

### 2.8 验证脚本其它实测修正

- 临时目录中的 Java 冒烟测试用 `java -cp "$TMPD" T`，避免 classpath 问题。
- 未安装软件的三层验证中，第 ① 层即判 FAIL 是**预期行为**，如实反映环境状态，不算脚本错误。
- Sunshine 管理页用 Python `urllib` 访问 `https://localhost:47990` 时证书/SNI 可能导致探测失败，验证时应结合端口监听与服务状态综合判断，不必强依赖 HTTPS 探测结果。

## 三、通用规避原则

1. **环境信息先查文档**：任何版本/路径/端口/命令问题，先看 [`电脑开发环境信息.md`](电脑开发环境信息.md)，不自猜；缺项则实测后补进文档。
2. **验证分三层**：① 功能有没有 → ② 环境是否存在 → ③ 功能是否正常，可直接跑 [`环境验证脚本.py`](环境验证脚本.py)。
3. **Python 一律 `-m pip`** 并优先用虚拟环境，避免多版本污染。
4. **Windows 脚本**：`.cmd` 命令解析完整路径调用；跨工具链不要套娃调 `cmd.exe`/`powershell.exe`；服务状态优先用 ctypes API。
5. **ctypes 铁律**：凡涉及句柄/指针，显式声明 `restype` 与 `argtypes`，否则 64 位下必踩坑。
6. **磁盘与端口敏感**：装大件前看磁盘余量；端口冲突先排查 Sunshine/Tailscale 等常驻服务。
